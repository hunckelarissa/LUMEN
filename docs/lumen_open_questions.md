## 1. Morph-блок: открытые вопросы проектирования

### 1.1. Интроспекция истории
**Вопрос:** Как именно работает `morph_obj.history`?  
- Можно ли обратиться к конкретному шагу: `pipeline.history["clean"]`?  
- Возвращается ли diff состояния (до/после шага) или только факт выполнения?  
- Хранится ли снапшот `state` на каждом шаге или только имя + статус?  

**Текущее решение (v0.0.1):** History — список записей `{step: String, status: String}`. Минимальный вариант.  
**Нужно решить до:** v0.2

### 1.2. Композиция morph-блоков
**Вопрос:** Можно ли один morph-блок использовать внутри другого?  
- Как передаётся состояние между вложенными morph?  
- Наследуется ли history?  
- Можно ли «включить» morph как шаг другого morph?  

**Текущее решение (v0.0.1):** Композиция отложена. Morph-блоки не вкладываются.  
**Нужно решить до:** v0.2

### 1.3. Природа `state`
**Вопрос:** Что такое `state` внутри morph-блока?  
- Это обычный Map?  
- Специальный тип с ограничениями?  
- Может ли `state` содержать функции?  
- Может ли `state` содержать другие morph-объекты?  

**Текущее решение (v0.0.1):** `state` — живая структура (Map). Без ограничений на содержимое.  
**Нужно решить до:** v0.2

### 1.4. Стоимость в транспиляторе
**Вопрос:** Как morph-блок с историей ложится на транспилятор в C?  
- Каждый morph — дополнительная структура в памяти.  
- History растёт с каждым `.run()`. Какова стоимость?  
- Нужен ли GC для history или ручное управление?  

**Текущее решение:** Не рассматривалось. Прототип на Python не имеет этой проблемы.  
**Нужно решить до:** v0.3 (этап транспилятора)

## 2. Метаморфная парадигма: фундаментальные вопросы

### 2.1. Детерминизм при эволюции
**Вопрос:** Как обеспечить детерминизм, когда функции эволюционируют и типы трансформируются?  
- Если функция расширяется через `when` в разных файлах, зависит ли порядок от порядка загрузки?  
- Можно ли гарантировать, что одна и та же программа всегда даёт один результат?  

**Нужно решить до:** v0.2

### 2.2. Рост истории
**Вопрос:** Как избежать экспоненциального роста истории трансформаций?  
- Если morph запускается в цикле 10000 раз, history копится?  
- Нужна ли стратегия усечения (truncation), суммирования (summarization) или ротации?  
- Должна ли быть явная операция `clear_history()`?  

**Нужно решить до:** v0.2

### 2.3. Метаинформация в рантайме
**Вопрос:** Будет ли runtime-метаинформация доступна самому коду?  
- Может ли программа на LUMEN читать `state.history` и принимать решения на его основе?  
- Может ли программа интроспектировать типы в рантайме (уже есть `is` и `type()`)?  
- Может ли программа интроспектировать morph-объект (список шагов, их имена)?  

**Текущее решение (v0.0.1):** `.history` доступен. Остальное — не определено.  
**Нужно решить до:** v0.2

## 3. Архитектурные вопросы

### 3.1. Граф трансформаций
**Идея:** Язык не компилируется в классический машинный код, а транслируется в **граф трансформаций**.  
**Вопрос:** Это актуально? Если да — как это соотносится с текущим планом «транспилятор в C»?  
**Статус:** Требует обсуждения. Возможно, это перспектива v1.0+, а не v0.x.

### 3.2. Событийно-ориентированное исполнение
**Идея:** Исполнение событийно-ориентированное, с возможностью внешнего контроля над эволюцией.  
**Вопрос:** Это означает, что внешний процесс может «пошагово» управлять morph? Как отладчик?  
**Статус:** Интересная идея, требует проработки. v0.3+.

### 3.3. Распределённые процессы
**Идея:** Встроенная поддержка распределённых процессов (кластеры, микросервисы).  
**Вопрос:** Morph-блоки как единица распределения? State синхронизируется между узлами?  
**Статус:** Отложено до v1.0+.

## 4. Синтаксис и семантика: спорные моменты

### 4.1. Явная vs неявная метаморфность — ✅ РЕШЕНО
**Противоречие (историческое):** Ранее декларировалось: «Метаморфность должна быть явной. Никаких автоматических преобразований». Но текущая спецификация допускает неявные трансформации через операторы (`"42" + 1 → 43`).  
**Решение (зафиксировано 12.04.2026):** Концепция «двух режимов» принята окончательно: явный морфинг обязателен ВНУТРИ morph-блоков; неявные трансформации допускаются ВНЕ morph-блоков.  
**Формализовано в:** `docs/lumen_spec.md` §3.2 (вводный абзац «Два режима метаморфности»), `docs/lumen_tz.md` §3.3.

### 4.2. Альтернативный синтаксис (не принят, но зафиксирован)
Ранее предлагались конструкции, конфликтующие с текущим Ruby-style синтаксисом:
- `state { ... }` вместо `def ... end`  
- `transform ->` для переходов  
- `type T evolves from ...` для объявления типов  

**Статус:** Не принято в v0.0.1. Текущий синтаксис — Ruby-style (`def...end`, `morph...end`). Альтернативы сохранены здесь для возможного пересмотра.

### 4.3. Зарезервированные слова без семантики
Слова `become`, `grow`, `extend`, `require` зарезервированы, но их полная семантика не определена.  
**Вопрос:** Что они будут делать?  
- `become` — превращение объекта в другой тип целиком?  
- `grow` — семантическое накопление (числа → `+`, строки → конкатенация, списки → append)?  
- `extend` — добавление when-ветвей к функциям из других модулей?  
- `require` — предусловие в transform-шагах (ошибка при несоответствии)?  

**Нужно решить до:** v0.2

## 5. LLM-native: открытые вопросы

### 5.1. Правила оптимизации под LLM
Пять правил оптимизации под LLM, принятых частично:
1. Одна форма трансформации (без альтернатив) — **не формализовано**  
2. Линейность (запрет сложных вложений внутри transform) — **не формализовано**  
3. Явные шаги (одна операция — одна строка) — **рекомендация, не правило**  
4. `history(x)` доступна — **реализовано** как `.history`  
5. Ограниченный morph (`become x as string`, без магии) — **не определено**  

**Ключевой вывод (оттуда же):** «LLM не любят абстракции. Они любят повторяемые действия.»  
**Нужно:** Решить, какие из этих правил станут частью спецификации, а какие — рекомендациями.

### 5.2. Автогенерация `llms.txt`
**Вопрос:** Интерпретатор/компилятор генерирует `llms.txt` из `shadow`, `reason`, `explain` автоматически?  
**Статус:** Отложено до v0.2.

## 6. Концептуальные идеи для будущего (не потерять)

### 6.1. Trace-oriented programming
«Это может быть trace-oriented programming language — язык, где программа = трасса изменений.»  
**Статус:** Философская идея. Может повлиять на дизайн v1.0.

### 6.2. Равенство как путь
`a == b` означает «существует траектория, по которой поток a может достичь состояния b».  
**Вопрос:** Это философия или реальная семантика оператора `==`?  
- Если реальная — текущий `==` (числовое/посимвольное равенство) нужно пересмотреть.  
- Если философия — оставить `==` как есть, но описать в манифесте.  

**Текущее решение:** Философия. Оператор `==` работает классически.  
**Нужно:** Явно зафиксировать это решение в спецификации.

### 6.3. «Переменных не существует»
«Переменных не существует. Есть только потоки состояний.»  
**Вопрос:** Это влияет на синтаксис (`x = 42` остаётся) или только на ментальную модель?  
**Текущее решение:** Ментальная модель. Синтаксис присваивания остаётся.

### 6.4. Два режима языка
Свободный режим (BASIC-like, live-coding) vs morph-режим (структурированный, с историей).  
**Вопрос:** Это формализуется как два явных режима или остаётся неявным (код вне morph = свободный, внутри morph = строгий)?  
**Нужно решить до:** v0.2

## 7. Синтаксические идеи из notes (не приняты, но перспективны)


### 7.1. Темпоральный доступ к истории потока
**Источник:** Заметки Qwen.txt  
**Идея:** Встроенный синтаксис для обращения к прошлым состояниям потока:
- `x.now` — текущее значение
- `x.was(5min ago)` — значение 5 минут назад (нужен внутренний таймстамп)
- `x.origin` — начальное значение при инициализации

**Зачем:** Это делает append-only историю не просто философией, а рабочим инструментом. Код может реагировать на прошлое, а не только на настоящее.  
**Связь:** Расширяет концепцию `.history` (раздел 1.1) конкретным синтаксисом.  
**Открытый вопрос:** Нужен ли реальный таймстамп или достаточно индексации по шагам (`x.was(3 steps ago)`)?  
**Нужно решить до:** v0.3+

### 7.2. Ключевое слово `self` в morph-блоках
**Источник:** формальные механизмы метаморфности.txt  
**Идея:** Внутри `morph`-блока `self` ссылается на текущее значение/объект:
```
morph number
    transform double
        return self * 2
    end
end
```
Тогда: `5.double()` → `10`.

**Зачем:** Позволяет morph-блокам быть не только state machines, но и **расширениями типов** (аналог extension methods в Kotlin/Swift).  
**Открытый вопрос:** Это второе назначение morph-блока (первое — state machine). Допускаем ли мы два вида morph, или это должны быть разные конструкции?  
**Нужно решить до:** v0.2

### 7.3. Morph-блоки как расширения типов
**Источник:** формальные механизмы метаморфности.txt  
**Идея:** Morph может не только описывать state machine, но и **добавлять методы** к существующим типам:
```
morph number
    transform square
        return self * self
    end
end
```
После чего `42.square()` → `1764`.

**Зачем:** Это позволяет LUMEN расширять даже встроенные типы без наследования. Ближе к Smalltalk/Ruby, чем к Java.  
**Конфликт:** Текущий `morph` — это блок с `state`, `history`, `.run()`. Morph-как-extension — это что-то совсем другое.  
**Нужно решить до:** v0.2 — определить, нужны ли два вида morph или другой синтаксис для расширений

### 7.4. Noise words — опциональные слова-связки
**Источник:** LIKE_COBOL.md  
**Идея:** Разрешить (но не требовать) слова-связки для читаемости:
- `add a to b giving c` вместо `c = a + b`
- `remove field from object` (уже есть)
- `transform data with clean` (уже есть)

Ключевой принцип: связки опциональны. `add a to b` и `add(a, b)` — оба работают.

**Зачем:** Делает код ещё ближе к естественному языку. LLM генерируют такой код естественно.  
**Риск:** Усложнение парсера. Неоднозначность при парсинге.  
**Связь:** Концепция «глагольного языка» (verb-based syntax, уже в TZ §3.5).  
**Нужно решить до:** v0.3+

### 7.5. Явный список anti-patterns
**Источник:** ChatGPT_LUMEN.md  
**Идея:** В спецификации или style guide явно перечислить запрещённые паттерны:

| Запрещено | Правильно | Почему |
|---|---|---|
| `x = x + 5` | `grow x with 5` | Нет семантики, просто мутация |
| `x \|> f \|> g` | `transform x with f` | Перегруженные символы |
| `transform x using f applying g` | `transform x with f` + `transform x with g` | Одна операция — одна строка |

**Зачем:** Это не просто стиль — это часть философии «один глагол — одно действие». Фиксация anti-patterns помогает и людям, и LLM генерировать идиоматический код.  
**Нужно решить до:** v0.2 (как часть style guide)

## 8. Архитектурные идеи из notes (не реализованы)

### 8.1. Type-space как метрическое пространство
**Источник:** Заметки DeepSeek.txt, Заметки Qwen.txt  
**Идея:** Типы находятся в метрическом пространстве, где расстояние = минимальное количество шагов трансформации между типами.

- `distance(String, Number) = 1` (один `as Number`)
- `distance(String, List) = ?` (может быть `parse → split`)
- Диссонанс = расстояние между текущим состоянием и ожидаемым типом

**Зачем:** Позволяет формализовать «степень совместимости» типов, а не бинарное «совместимы / не совместимы». Оператор `~=` (path equivalence) можно определить как «расстояние конечно».  
**Математическая база:** Это естественно ложится на HoTT (раздел 6.2).  
**Связь:** OQ-4 (диссонанс), OQ-5 (path equivalence) в lumen_todo.md.  
**Нужно решить до:** v0.3+ (исследование)

### 8.2. Flow IR — промежуточное представление
**Источник:** ChatGPT_LUMEN.md  
**Идея:** Архитектура компилятора не `Source → AST → Interpreter`, а:
```
Source → Parser → Flow IR → Execution Engine → Trace Engine
```
Flow IR (Intermediate Representation) — специализированное представление, которое явно моделирует потоки, шаги и состояния. Это не просто «ещё один AST», а граф потоков с аннотациями типов-траекторий.

**Зачем:** Упрощает оптимизацию (можно анализировать потоки статически), транспиляцию (Flow IR → C проще, чем AST → C), и LLM-генерацию (LLM может генерировать IR напрямую).  
**Статус:** Текущий план — классический AST → Interpreter. Flow IR — потенциальная замена для v0.3+.

### 8.3. Прототип на Python: конкретный blueprint
**Источник:** Заметки DeepSeek.txt  
**Идея:** Конкретная архитектура для быстрого proof-of-concept (ДО полного интерпретатора):
- Класс `Flow` с начальным состоянием и списком разрешённых трансформаций
- Метод `.transform(step)` — применяет шаг, записывает в историю
- Свойство `.dissonance` — евклидово расстояние в пространстве шагов
- Функция `equal_as_path(a, b)` — BFS в графе переходов

**Зачем:** Можно за день сделать работающую демку, которая покажет концепции в действии ДО готовности интерпретатора.  
**Статус:** Не реализовано. Приоритет — после MVP интерпретатора.

## 9. Философские концепции и фреймворки

### 9.1. Программа как трасса (execution trace language)
**Источник:** ChatGPT_LUMEN.md, LUMEN-LN.md  
**Идея:** LUMEN — не «язык, который создаёт трассу», а «язык, где программа ЯВЛЯЕТСЯ трассой». Каждая строка — шаг. Каждый flow — последовательность состояний. Программа = упорядоченный лог изменений.

**Зачем:** Это меняет ментальную модель: вместо «я пишу инструкции, которые выполняются» — «я описываю путь, который проходит сущность».  
**Связь:** Trace-oriented programming (раздел 6.1).  
**Открытый вопрос:** Если программа = трасса, то отладка = просмотр программы? Debug-by-default?

### 9.2. «Один flow = одна идея»
**Источник:** LUMEN-LN.md  
**Принцип:** Каждый flow-блок должен представлять ровно одну концептуальную единицу. Если flow делает две вещи — разбей на два.

**Зачем:** Когнитивная простота. LLM генерирует один flow за раз — это предсказуемо.  
**Связь:** Принцип Single Responsibility, но на уровне потока, а не класса.  
**Статус:** Конвенция, не жёсткое ограничение.

### 9.3. Chain-of-thought как код
**Источник:** LUMEN-LN.md  
**Идея:** Рассуждения LLM напрямую выражаются как flow-блоки:
```
flow reasoning from input
    step analyze
    step transform
    step evaluate
end
```
Это не метафора — это реальная структура, которую LLM может генерировать и выполнять.

**Зачем:** Превращает LUMEN в «язык мышления для ИИ». Каждый шаг — отдельная мыслительная операция, с трассировкой.  
**Связь:** LUMEN-LN (R-2 в lumen_todo.md), LLM-native конструкции.

### 9.4. Legacy without erasure — мёртвый код как история
**Источник:** Заметки Qwen.txt  
**Идея:** Старый код (в т.ч. deprecated, deadcode) не удаляется физически, а помечается как «исторический контекст». Он не активен, но он часть пути объекта/модуля. Git-история не переписывается, а дополняется метаданными о трансформации.

**Зачем:** Это прямое отражение append-only семантики LUMEN в контексте разработки самого кода. Код эволюционирует, а не «рефакторится до неузнаваемости».  
**Связь:** Append-only history (spec §VII), философия метаморфности.  
**Открытый вопрос:** Нужна ли специальная аннотация? Что-то вроде `deprecated "reason"` или `historical "context"`?

### 9.5. Ключевая аналогия для объяснения LUMEN
**Источник:** Claude.txt, Мнение Grok.md  
**Формулировка:**

> «morph — для LUMEN то же, что async/await для JavaScript, ownership для Rust, монады для Haskell»

Это **центральная** фраза для всей коммуникации проекта. Она:
- Сразу задаёт масштаб амбиции
- Показывает, что это не «ещё один синтаксический сахар»
- Понятна любому программисту, знакомому хотя бы с одним из этих языков

**Использовать:** В README, на главной странице, в первых строках любой презентации.

### 9.6. Конкретные ниши, не вошедшие в TZ
**Источник:** Claude.txt, Мнение Grok.md, Мнение Copilot.md  
Помимо уже зафиксированных ниш (data/ML pipelines, LLM-агенты, state machines), в notes упоминались:
- **Бизнес-процессы:** заявка → рассмотрение → одобрение → исполнение
- **Жизненный цикл объектов в играх:** spawn → alive → hit → dead → respawn
- **Сетевые протоколы:** TCP/HTTP как цепочки состояний (SYN → SYN-ACK → ESTABLISHED → ...)
- **Компиляторы:** каждый проход по AST — это трансформация состояния (ирония: LUMEN сам себя описывает)
- **Текстовые игры / interactive fiction:** morph-блоки как комнаты/предметы с состояниями

**Зачем:** Готовый список для killer-примеров (D-1 в lumen_todo.md).

## 10. Маркетинг и позиционирование

### 10.1. Community launch strategy
**Источник:** Мнение Grok.md  
**Порядок запуска (рекомендованный):**
1. 3–5 killer-примеров (data pipeline, LLM-агент, state machine, live-coding)
2. Минимум синтаксиса, покрывающий эти примеры
3. Работающий прототип (интерпретатор)
4. 7-минутное видео «LUMEN за 7 минут» с демонстрацией
5. Выложить всё разом: репозиторий + видео + манифест + примеры

**Площадки (в порядке приоритета):**
- r/ProgrammingLanguages
- r/Compilers
- X / Mastodon (#ProgrammingLanguage #QueerInTech)
- Lobsters / Hacker News (после первых отзывов)

### 10.2. Уровень позиционирования
**Источник:** Мнение Copilot.md  
Манифест LUMEN потенциально может встать в один ряд с:
- «Why Functional Programming Matters» (John Hughes)
- «Out of the Tar Pit» (Moseley, Marks)

Ключевая формулировка для этого уровня:
> «Все существующие языки отвечают на вопрос "как вычислить". LUMEN отвечает на вопрос "как нечто становится другим".»

### 10.3. Стратегия вирусности
**Источник:** Мнение Grok.md  
**Принцип:** Вирусность через идею + исполнение, а не через идентичность. Когда идея острая и примеры бьют в цель — транс-авторство станет заметным само и сработает как усилитель, а не как основной двигатель.

**Практически:** Не «продавать транс-авторство» — а делать код и примеры настолько хорошими, что идентичность автора усиливает историю, а не подменяет её.
