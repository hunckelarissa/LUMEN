## 1. Общие сведения

### 1.1. Наименование проекта
Язык программирования **LUMEN** — язык общего назначения с минимальным ядром, основанный на **метаморфной парадигме**.

### 1.2. Назначение
Создание реального, применимого, хорошо документированного языка программирования, способного использоваться для обучения, прототипирования, написания скриптов и создания DSL. Язык ориентирован на выразительность, гибкость и низкий порог входа.

### 1.3. Авторство и контекст
Язык разрабатывается Ларисой — программисткой с практическим опытом создания интерпретаторов, транспиляторов и доработки компиляторов (Школьный Алгоритмический Язык, Euler, Mesa, Cedar, Euclid, форки GNU-компиляторов).

### 1.4. Слоган
*"A language that evolves with you."*  
*«Язык, который развивается вместе с тобой.»*

**Дополнительные формулировки:**  
*"Code that transforms. Ideas that grow."*  
*"Not static. Not dynamic. Alive."*  
*«Не вычисления, а процессы.»*

### 1.5. Философская основа

Код — **живая структура**, которая эволюционирует через состояния.  
Язык описывает не алгоритм, а **трансформацию сущности**.  
Центральный вопрос LUMEN — не «как вычислить результат?», а **«как нечто становится другим?»**

> В LUMEN программа может описывать не только то, что происходит,  
> но и то, **как нечто становится другим**.

Это делает LUMEN **языком описания эволюции состояний** (state evolution language).

### 1.6. Математическая основа

Формальная семантика LUMEN опирается на концепции, родственные **Гомотопической Теории Типов (HoTT)**:

- **Тип — не множество значений, а множество допустимых траекторий** трансформаций через пространство состояний.
- **Равенство — это путь** (философская модель): в метаморфном контексте `a` и `b` считаются эквивалентными, если существует последовательность допустимых трансформаций между ними (path equivalence). В v0.1 оператор `==` реализован как классическое сравнение значений; path equivalence — концепция для исследования в будущих версиях.
- **Присваивание — продолжение траектории**: `x = expr` не перезаписывает ячейку, а добавляет новое состояние к потоку.
- **История — монотонно растущая**: каждая трансформация добавляет запись, ничего не удаляется (append-only semantics).

Формально: поток `x: N → V` (функция времени в значения), тип `T ⊆ V^N` (множество допустимых последовательностей), морфинг — морфизм `f: T₁ → T₂`.

> Формальная семантическая модель описана в `lumen_spec.md`, Часть VII.

### 1.7. Целевая аудитория и ниши

LUMEN позиционируется как язык для задач, где **эволюция состояния** является естественной моделью:

| Ниша | Почему LUMEN здесь силён |
|---|---|
| **Data / ETL / ML pipelines** | Обработка данных — цепочка трансформаций: clean → enrich → aggregate → train. `morph`-блок — идеальная абстракция |
| **LLM-агенты / agentic workflows** | Цикл observe → reason → act = `morph`-блок. Язык нативно описывает ReAct-паттерн |
| **State machines / workflow engines** | Бизнес-процессы, игры, IoT — конечные автоматы с именованными переходами |
| **Live-coding / creative tools** | Мгновенная адаптация под новые типы и контексты |
| **Прототипирование DSL** | Быстрое добавление новых правил без изменения ядра |
| **Образование** | Низкий порог входа, «язык прощает и позволяет экспериментировать» |
| **Персональная автоматизация** | Скрипты, второй мозг, evolving data |

**Антиниши** (где LUMEN не является оптимальным выбором):
- Крупный корпоративный бэкенд с 50+ разработчиками (Go, Java)
- Критические production-системы с нулевой толерантностью к сюрпризам (Rust)
- Большие SPA-приложения (TypeScript)

## 2. Цели и требования верхнего уровня

### 2.1. Главные цели
1. Создать **реально работающий** язык, а не академическую игрушку или мем-проект типа INTERCAL.
2. Реализовать **метаморфную парадигму** — новую концепцию, не являющуюся производной ООП, функциональной, логической или реактивной парадигм.
3. Обеспечить **кроссплатформенность**: Linux (основная платформа), Windows, macOS.
4. Обеспечить **качественную документацию** с порогом входа «10 минут до первой программы».
5. Создать **экосистему** для роста сообщества: репозиторий, CLI, REPL, форматтер.

### 2.2. Антицели (явно НЕ делаем)
- Не стремимся к универсальности уровня PL/I или ALGOL-68.
- Не создаём эзотерический язык (не INTERCAL, не Brainfuck).
- Не копируем Python/Ruby/Go.
- Не требуем JIT и нативных оптимизаций на первом этапе.
- Не реализуем многопоточность в ядре v0.1.

## 3. Метаморфная парадигма — ключевая концепция

### 3.1. Определение
Метаморфная парадигма — подход, при котором код рассматривается как **живая структура**, способная трансформироваться, адаптироваться и эволюционировать. Парадигма включает четыре ключевых механизма:

| Механизм | Суть |
|---|---|
| Трансформация типов | Значения переходят между типами по формальным правилам |
| Эволюция функций | Функция расширяет поведение путём добавления новых правил |
| Живые структуры | Объекты/карты изменяют состав полей в процессе выполнения |
| Контекстная адаптация | Контекст исполнения влияет на интерпретацию операций |
| Morph-блоки | Именованные цепочки трансформаций состояния — первоклассная абстракция языка |
| История трансформаций | Каждый morph-объект хранит append-only лог трансформаций. В v0.1 история доступна для чтения (`.history`); откат (`undo`) и форк запланированы на v0.3+ |
| Диссонанс | Переход вне допустимого множества трансформаций — не крах, а сигнал напряжения. Обрабатывается в зависимости от режима (strict/soft/creative). В v0.1 — только strict (= TransformError) |

### 3.2. Killer Feature

> **LUMEN — первый язык, в котором эволюция состояния является первоклассной языковой абстракцией, а не библиотекой.**

Конкретно это означает:
1. **`morph`-блок** — языковая конструкция (не библиотека, не декоратор), которая объявляет именованное состояние и цепочку его трансформаций.
2. **`transform`-шаги** — именованные, компонуемые, прозрачные; язык знает об их существовании и может их интроспектировать.
3. **История трансформаций** встроена в рантайм: каждый `morph`-объект помнит, через какие шаги он прошёл.
4. **Вне `morph`-блоков** — обычный язык с динамической типизацией, свободой и читаемостью в духе Ruby.

### 3.3. Философские аксиомы

1. **Состояние — это процесс**, а не значение. Оно всегда в движении.
2. **Тип — это траектория** движения потока, а не фиксированная метка.
3. **Морфинг — основной механизм изменения**. Все изменения в morph-блоках происходят через явные трансформации.
4. **История встроена** в каждую сущность — полная траектория трансформаций.

**Дизайн-решение: два режима метаморфности.**  
Язык LUMEN формально определяет два режима трансформаций:
- **Свободный режим** (вне morph-блоков): неявные трансформации через операторы допускаются (`"42" + 1 → 43`). Язык ведёт себя как динамический с гибкой типизацией.
- **Строгий режим** (внутри morph-блоков): все изменения state происходят через явные операции в transform-шагах. Каждый шаг именован, логируется в history, может быть условно пропущен через `skip if`.

Это не противоречие, а осознанный дизайн: morph-блоки — зона контроля и трассируемости, остальной код — зона свободы и выразительности.

### 3.4. Отличие от существующих парадигм
- **vs ООП**: объекты не фиксированы; наследование не является основным механизмом.
- **vs Функциональная**: функции не являются чистыми; состояние допускается; эволюция функций отсутствует в классическом FP.
- **vs Динамическая типизация**: переходы типов формализованы и предсказуемы, не хаотичны.
- **vs Gradual typing (TypeScript)**: не просто аннотации — реальные правила трансформации.
- **vs Pipelines (Elixir `|>`, F#)**: `morph`-блоки — не просто синтаксис цепочек. Шаги именованы, интроспектируемы, компонуемы, с встроенной историей.
- **vs State machines (XState)**: XState — библиотека только для конечных автоматов. В LUMEN `morph` — нативная конструкция для общего случая эволюции состояния.
- **vs Icon**: Icon предложил goal-directed evaluation и цепочки результатов. LUMEN берёт похожую интуицию (цепочки состояний), но пересаживает её в 2026 год: data pipelines, LLM-агенты, встроенная история.
- **vs COBOL**: COBOL был «слишком человеческим» для программистов, но именно глагольная модель (verb-based syntax) делает его идеально понятным для машин, обученных на тексте. LUMEN наследует принцип глагольности (transform, morph, grow) без многословности COBOL.
- **vs dbt + Prefect + LangChain**: Эти инструменты решают задачи data/agent pipelines поверх Python. LUMEN предлагает единый coherent язык для описания тех же процессов нативно.

### 3.5. Дизайн-принципы синтаксиса

Синтаксис LUMEN следует принципу **«глагольности»** — каждая ключевая конструкция названа действием:

| Глагол | Действие |
|---|---|
| `morph` | объявить эволюционирующую сущность |
| `transform` | именованный шаг трансформации |
| `skip` | условный пропуск шага |
| `remove` | удалить поле из объекта |
| `break` | выход из цикла |
| `continue` | пропуск итерации цикла |
| **Будущее:** `grow` | семантическое накопление (v0.2) |
| **Будущее:** `become` | явная смена типа/структуры (v0.2) |
| **Будущее:** `extend` | добавление правил к существующей функции (v0.2) |
| `require` | предусловие шага внутри `transform`: ложное условие — `MorphError` |

## 4. Требования к синтаксису

### 4.1. Общие принципы
- Синтаксис **выразительный и читаемый** — как Ruby, а не многословный как Java.
- **ЗАПРЕЩЕНО** использование отступов для выделения блоков (no Python-style indentation).
- Блоки кода **явно открываются и закрываются** ключевыми словами (в духе Ruby: `do...end`, `if...end`, `def...end`).
- Комментарии — через `#`.
- Строки — в двойных кавычках `"..."`.
- Идентификаторы: латиница, цифры, подчёркивание; первый символ — буква или `_`.

### 4.2. Обязательные конструкции ядра

#### Присваивание
```
x = выражение
```

#### Объявление функции (Ruby-стиль)
```
def имя(параметры)
  тело
end
```

#### Условие
```
if условие
  блок
else
  блок
end
```

#### Цикл for
```
for элемент in коллекция
  блок
end
```

#### Цикл while
```
while условие
  блок
end
```

#### Break и continue
```
for i in range(10)
  if i == 5
    break
  end
end

while n < 100
  n = n + 1
  if n % 2 == 0
    continue
  end
  print(n)
end
```

#### Эволюция функции (специфика LUMEN)
```
def show(v)
  when Number then print("number: ", v)
  when String then print("string: ", v)
  when List   then print("list of ", len(v), " items")
end
```

#### Трансформация типа (явная)
```
x = "42"
y = x as Number     # явное приведение
z = x + 1           # неявная трансформация через оператор
```

#### Доступ к полям и расширение объекта
```
user = {name: "Lara"}
user.age = 30
user.tags = ["dev", "creator"]
```

#### Объявление контекста
```
context web
  print("Hello")   # → HTML-вывод
end

context cli
  print("Hello")   # → stdout
end
```

#### Morph-блок (эволюция состояния)
```
morph dataset
  state rows: List
  state cleaned: Boolean = false

  transform "clean"
    state.rows = remove_nulls(state.rows)
    state.cleaned = true
  end

  transform "normalize"
    skip if state.cleaned == false
    state.rows = scale(state.rows, "zscore")
  end

  transform "extract"
    state.features = pca(state.rows, 10)
  end
end

dataset.run()            # запускает все трансформации по порядку
print(dataset.history)   # встроенная история трансформаций
```

#### LLM-native конструкции
```
# Теневая документация (видна LLM, игнорируется интерпретатором)
shadow "LLM: treat this as ReAct loop"

# Маркер мышления (встроенный chain-of-thought)
think "Current state: goal=classify, observation=raw data"

# Рассуждение внутри transform
reason "Нужно сначала проверить cleaned флаг"

# Объяснение для истории
explain "this step reduces nulls by 87%"

# Аннотация в комментариях
# @llm: this morph is a data pipeline
```

## 5. Требования к типовой системе

### 5.1. Базовые типы ядра

| Тип | Описание |
|---|---|
| `Number` | Единый числовой тип (целые + вещественные, внутренняя реализация на усмотрение) |
| `String` | Unicode-строки |
| `Boolean` | `true` / `false` |
| `List` | Упорядоченная коллекция, произвольные элементы |
| `Map` | Ассоциативный массив, ключи-строки |
| `Function` | Функция первого класса |
| `Context` | Объект окружения исполнения |
| `Morph` | Объект morph-блока с состоянием, шагами и историей |
| `Null` | Отсутствие значения |

### 5.2. Правила трансформации типов (обязательные для ядра)

| Откуда | Куда | Условие | Результат при неудаче |
|---|---|---|---|
| `String` | `Number` | строка содержит корректное число | `TransformError` |
| `Number` | `String` | всегда | успех |
| `Boolean` | `Number` | всегда | `true→1`, `false→0` |
| `Number` | `Boolean` | всегда | `0→false`, иначе `true` |
| `List` | `String` | всегда | строковое представление |
| `Map` | `String` | всегда | строковое представление |

### 5.3. Неявные трансформации через операторы
Оператор `+` может инициировать трансформацию:
- `"42" + 1` → `Number("42") + 1` → `43`
- `42 + "!"` → `String(42) + "!"` → `"42!"`
- Правило: **левый операнд определяет целевой тип** (при неоднозначности).

### 5.4. Явная трансформация
Оператор `as`:
```
x = "42" as Number    # 42
y = 3.14 as String    # "3.14"
```

### 5.5. Проверка типа
Оператор `is`:
```
if x is Number
  print("это число")
end
```

## 6. Требования к модели исполнения

### 6.1. Контекст исполнения
- Каждый фрагмент кода исполняется в **контексте**.
- Контекст определяет: режим вывода, доступные модули, правила адаптации.
- Контекст передаётся **неявно** (не требует явного указания в простых случаях).
- Расширенные контексты (`web`, `gui`) — в модулях, не в ядре.

**Контексты ядра v0.1:**

| Контекст | Описание | Поведение `print` |
|---|---|---|
| `cli` | По умолчанию. Стандартный ввод/вывод. | Вывод в stdout |
| `test` | Тестовый режим. | Вывод перехватывается тестовым раннером; `print` записывает в буфер, а не в stdout |

Встроенные функции могут запрашивать текущий контекст через `type(context)`. Пользовательские контексты в v0.1 не влияют на поведение встроенных функций, но устанавливают именованную область видимости.

### 6.2. Эволюция функций
- Функция может иметь несколько **ветвей** `when`, покрывающих разные типы аргументов.
- Добавление новой ветви `when` в уже объявленную функцию — **расширение**, не переопределение.
- Порядок проверки ветвей: сверху вниз, первое совпадение.
- Если ни одна ветвь не совпала и нет ветви по умолчанию — `DispatchError`.

### 6.3. Живые структуры (Map)
- Поля карты можно добавлять и изменять в любой момент.
- Удаление поля — явной операцией `remove поле from объект`.
- Доступ к несуществующему полю возвращает `null` (не ошибку).

### 6.4. Morph-блоки (модель исполнения)

- `morph` объявляет **именованное состояние** и последовательность **именованных шагов** его эволюции.
- Внутри `morph` доступен объект `state` — живая структура (Map), которая проходит через трансформации.
- Каждый `transform` — именованный шаг. Шаги выполняются последовательно при вызове `.run()`.
- `skip if условие` — условный пропуск шага.
- **История трансформаций** встроена: `morph_obj.history` возвращает лог всех пройденных шагов.
- Шаги **компонуемы**: можно именованно пропустить, заменить, добавить новые.
- `morph`-блоки создают собственную область видимости; `state` доступен только внутри блока.
- **Разрешение `state`:** синтаксически `state.field` — обычный `FieldAccess` на `Ident("state")`. Интерпретатор при входе в morph-блок связывает имя `state` с живой структурой (Map) этого morph-объекта. Вне morph-блоков `state` не имеет специального значения.
- **Различие Map и Morph:** тип `Map` — чистые данные без встроенных методов. Тип `Morph` — отдельный тип со встроенными свойствами `.run()`, `.history`, `.state`, реализуемыми интерпретатором через специальную логику (не через поля Map).

### 6.5. LLM-native конструкции

- `shadow "текст"` — теневая документация, игнорируется интерпретатором, видна LLM при анализе кода.
- `think "текст"` — блок для LLM-рассуждений, не исполняется. В v0.1 парсится и сохраняется в метаданных; использование для генерации промптов — перспектива v0.2+.
- `reason "текст"` — маркер мышления внутри `transform`, для chain-of-thought.
- `explain "текст"` — объяснение для истории трансформаций.
- `# @llm: текст` — аннотация в комментариях, собирается парсером в отдельный контекст для моделей.
- Интерпретатор/компилятор может автоматически генерировать файл `llms.txt` из всех `shadow`, `reason`, `explain`.

### 6.6. Область видимости
- Лексическая область видимости (static scoping).
- Функции захватывают переменные из внешней области (замыкания).
- Глобальная область видимости — для переменных, объявленных вне функций.

## 7. Требования к реализации

### 7.1. Фазы разработки

#### Фаза 1 — Прототип на Python (приоритет)
- Лексер
- Парсер (ручной рекурсивный спуск)
- AST
- Интерпретатор AST
- REPL
- Базовые встроенные функции

#### Фаза 2 — Транспилятор LUMEN → C
- Генерация C-кода из AST
- Минимальный рантайм на C
- Сборка через gcc/clang
- CLI-инструмент

#### Фаза 3 — Нативный рантайм на C++ (перспектива)
- Оптимизация исполнения
- Расширяемая система типов
- FFI для вызова C-кода

### 7.2. Требования к инструментарию
| Инструмент | Требование |
|---|---|
| `lumen run <file>` | Интерпретация файла |
| `lumen repl` | Интерактивный режим |
| `lumen compile <file> -o <out>` | Компиляция через транспилятор |
| `lumen fmt <file>` | Форматирование кода |
| `lumen version` | Вывод версии |

### 7.3. Требования к платформам
- **Linux** (x86_64, ARM64) — основная платформа разработки
- **Windows** (x86_64) — обязательная поддержка
- **macOS** — желательная поддержка

### 7.4. Требования к тестированию
- Покрытие тестами ядра: не менее 70% для v0.1.
- Обязательные категории тестов:
  - тесты лексера (токенизация)
  - тесты парсера (корректность AST)
  - тесты интерпретатора (семантика)
  - тесты трансформаций типов
  - тесты эволюции функций
  - тесты обработки ошибок
  - golden-тесты для вывода программ

### 7.5. Требования к morph-блоку в v0.1
- Парсер должен распознавать `morph`, `transform`, `state`, `skip`, `shadow`, `think`, `reason`, `explain`.
- Интерпретатор должен выполнять morph-блоки с последовательными transform-шагами.
- Объект `state` внутри morph должен быть живой структурой (Map).
- Метод `.run()` должен запускать все трансформации.
- `.history` должен возвращать лог выполненных шагов.
- `shadow`, `think`, `reason`, `explain` — парсятся, но не исполняются (сохраняются в метаданных).
