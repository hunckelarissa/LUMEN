3. Ключевые понятия (глоссарий — только то, что точно осталось)

    Метаморфная парадигма: тип не фиксирован, он становится; функция — это последовательность состояний, а не отображение аргумента в результат.

    Живые структуры: данные могут менять свою структуру в рантайме, но с контролируемой историей.

    Контекстная адаптация: поведение кода зависит от окружения выполнения (не только от типов, но и от «истории вызова»).

    Эволюция функций: функция может быть переопределена на лету, при этом старые вызовы продолжают работать по старому определению, если это нужно.

    История (как механизм): каждый объект/тип/функция хранит свою цепочку изменений — можно откатиться, форкнуть, проанализировать.
    
3a.Ключевые понятия с объяснениями (пункт подлежит обсуждению и изменению!!! примеры наверное устаревшие!!!)
    1. «Типы могут переходить из одного состояния в другое»
    Что это значит на практике
    Это не магия. Это типовая система, где тип — не фиксированная метка, а состояние объекта.
    Пример из реальной жизни:
        строка "123" может переходить в число 123
        число 123 может переходить в строку "123"
        структура может расширяться по мере выполнения программы
        объект может менять форму, когда появляются новые поля
    То есть тип — это не бинарное «строка или число», а путь, по которому объект может двигаться.
    Зачем это нужно
        меньше boilerplate
        меньше ручных преобразований
        более гибкий код
        возможность писать «живые» DSL
        удобство для новичков
        мощь для экспертов
    Это не игрушка — это реально полезно.
    2. «Функции могут эволюционировать»
    Что это значит
    Функция может менять своё поведение в зависимости от:
        типов аргументов
        контекста вызова
        окружения
        предыдущих вызовов
        состояния программы
    Это не «магия», это многоформенность + адаптивность.
    Пример:
    func add(a, b):
        if both numbers -> numeric addition
        if both strings -> concatenate
        if list + element -> append
        if element + list -> prepend
    end
    То есть одна функция растёт, обрастает поведением, адаптируется.
    Зачем это нужно
        меньше перегрузок
        меньше однотипных функций
        более выразительный код
        возможность писать естественные DSL
    3. «Объекты могут менять форму»
    Что это значит
    Это структуры, которые могут расширяться, сжиматься, менять поля.
    Пример:
    user = {name: "Lara"}
    user.age = 30
    user.contacts = []
    Это уже есть в Python, JS, Lua — но можно сделать это типобезопасным и контролируемым.
    Зачем это нужно
        гибкость
        удобство
        возможность писать код «как думаешь»
        создание динамических моделей данных
    4. «Код адаптируется к контексту»
    Что это значит
    Контекст — это:
        где вызывается функция
        какие типы вокруг
        какие модули подключены
        какое состояние у программы
        какой режим работы выбран
    Пример:
    print(x)
    В зависимости от контекста:
        в CLI > текст
        в GUI > всплывающее окно
        в web > HTML
        в логгер > запись в файл
    Это не хаос — это контекстные правила, которые можно описать.
    Зачем это нужно
        меньше шаблонного кода
        язык становится «умным»
        можно писать DSL для разных областей
        код становится выразительным
    И да — это всё можно реализовать:
        через расширяемую типовую систему
        через многоформенные функции
        через динамические структуры
        через контекстные правила
        через метапрограммирование
        через адаптивный рантайм
    Было ли что-то похожее?
    Языки с изменяемыми типами?
        Есть динамическая типизация (Python, JS), есть gradual typing (TypeScript), есть dependent types (Idris).
        Но переходы типов как концепция — нет.
    Языки с эволюционирующими функциями?
        Есть multimethods (Clojure), есть pattern matching (Haskell), есть overloads (C++).
        Но функция, которая растёт и адаптируется — нет.
    Языки с изменяемой формой объектов?
        Есть прототипы (JS), есть метаклассы (Python), есть макросы (Lisp).
        Но объект как живая структура, меняющая форму по правилам — нет.
    Код, адаптирующийся к контексту?
        Есть context managers, есть implicit parameters (Scala), есть traits (Rust).
        Но контекст как первоклассная сущность, влияющая на поведение языка — нет.
    Парадигма, объединяющая всё это?
        Нет.
        Вообще нет.
        А теперь это Метаморфная парадигма!

    Главная фишка: язык, который отражает идею трансформации, как архитектурный принцип

    код может адаптироваться к контексту
    LUMEN - язык, который знает, зачем он существует.
    Очень важное правило: Метаморфность должна быть явной. То есть никаких автоматических преобразований.    
    Где метаморфность действительно полезна:
        Data pipelines. Обработка данных — это почти всегда цепочка преобразований.
        ML / AI pipelines. Интересный факт: почти весь ML — это метаморфозы данных.
        Game state / simulations. Игры и симуляции — это эволюция состояния мира.
        Event processing systems. Например: стриминг, обработка событий, лог-пайплайны
        Domain-specific DSL. Иногда язык нужен не как универсальный инструмент, а как способ описывать процессы.
        Метаморфность лучше всего работает, когда программа — это: state evolution а не control logic
    Настоящая ценность идеи - Метаморфность — это не просто синтаксис. Это другая ментальная модель программирования. Обычная модель: команды изменяют состояние, а метаморфная: состояние проходит через трансформации
    Очень важное наблюдение - Если сделать метаморфность всего языка, получится странно. Но если сделать её первоклассным механизмом, получится мощно. Это не весь язык, а ключевая абстракция.
    Метаморфность не пустышка, но её сила проявляется не везде. Она максимально полезна там, где программы — это: данные > трансформации > результат, то есть: data processing, ML pipelines, simulations, event streams
    И вот здесь появляется очень интересная идея, которая может сделать Lumen реально уникальным: вместо того чтобы быть просто языком программирования, он может стать языком описания эволюции состояний. Это совершенно другая ниша среди языков — и там почти нет конкурентов.
    Lumen — язык эволюции состояния, пригодный для интерактивного творчества и формальных программ.
    язык преобразования значений и потоков.
    Состояние — это процесс, а тип — это траектория. переменных не существует! есть инициация потока, его трансформация, покрытая диссонансами, есть морфинг/кастование типов, есть тип в виде траектории, или в виде пространств(?), где равенства - путь(?), где ячейки хранят историю изменений
    Это не просто язык. Это может быть: trace-oriented programming language (язык, где программа = трасса изменений)
    метаморфность — это модель изменения состояния, а не просто синтаксическая фишка. метаморфность описывает цепочку преобразований состояния. Это ближе к тому, как описываются процессы, а не просто вычисления. Где это реально полезно

10.Как сделать Lumen максимально LLM-friendly
    Правило 1 — одна форма трансформации
        transform x with f
        и НИКАКИХ альтернатив.
    Правило 2 — линейность
        Запрещать сложные вложенные конструкции внутри transform.
    Правило 3 — явные шаги
        Каждая операция — новая строка.
    Правило 4 — история доступна
        history(x)
    Правило 5 — ограниченный morph
        become x as string
        но без магии.
    Самый важный вывод - LLM не любят абстракции. Они любят повторяемые действия.

  end

**Основные аксиомы LUMEN (v0.1)**

1. **Переменных не существует.**  
   Существуют только **потоки состояний** (state flows). Поток начинается с инициации (`morph` или `let`) и живёт через последовательность трансформаций.

2. **Состояние — это процесс.**  
   Состояние никогда не бывает статичным. Оно всегда находится в движении — даже если в данный момент ничего не происходит.

3. **Тип — это траектория.**  
   Тип не является точкой, а является **путём**, который поток уже прошёл и может пройти дальше. Тип описывает возможное пространство трансформаций.

4. **Морфинг — основной механизм изменения.**  
   Все изменения происходят через явный морфинг (`as`, `transform`, `become`). Неявных кастований нет.

5. **История встроена в каждую ячейку.**  
   Каждая сущность (state) хранит не только текущее значение, но и **полную траекторию** своих трансформаций, включая все диссонансы (моменты, когда типы конфликтовали и требовался морфинг).

6. **Равенство — это путь, а не точка.**  
   `a == b` означает «существует траектория, по которой поток a может достичь состояния b».

### Вариант 3. Расширенный, поэтичный, но уже формальный (для отдельного файла philosophy.md или введения в morph.md)

**Онтология LUMEN: Состояние как процесс**

В традиционных языках переменная — это коробка, в которую кладут значение.  
В LUMEN **коробок нет**.

Есть только **поток**.  
Поток рождается в момент инициации.  
Он течёт через пространство возможных состояний.  

**Тип** — это не ярлык на коробке и не класс.  
Тип — это **траектория** потока: кривая, которую он уже описал и может описать в будущем.  
Тип — это **пространство допустимых трансформаций**.

**Морфинг** — это осознанное изменение направления траектории.  
Каждый `transform`, каждый `as`, каждый `become` — это поворот потока, который мы явно фиксируем.

В каждой точке пространства хранится не «текущее значение», а **вся история пути**:  
все предыдущие состояния, все диссонансы (моменты, когда поток «споткнулся» о несовместимость типов), все успешные и неуспешные морфинги.  
Поэтому `state.history` — это не отладочная фича. Это **сущность языка**.

Равенство в LUMEN — тоже процесс:  
`a == b` означает «существует непрерывная траектория, по которой поток a может превратиться в b без потери информации».

### Почему это скорее **помогает** LLM (основные плюсы)

1. **Явные, именованные шаги трансформации**  
   morph-блоки с `transform "clean"`, `transform "normalize"`, `skip if …` — это почти **chain-of-thought в синтаксисе языка**.  
   LLM очень хорошо понимают и генерируют последовательные, пошаговые инструкции. Когда ты пишешь не `x = f(g(h(x)))`, а  
   ```
   morph data
     transform "clean"   …
     transform "normalize" …
   end
   ```  
   модель видит **явную структуру рассуждения** — ей гораздо легче не запутаться в том, что происходит с данными.

2. **История изменений встроена > меньше галлюцинаций о состоянии**  
   В классическом императивном коде LLM часто «забывают», что было в переменной 10 строк назад, и придумывают неверные мутации.  
   У тебя `state.history` — это **память потока**, которую модель может использовать как подсказку. Это снижает типичные ошибки: «я думал, что здесь уже очищено, а на самом деле нет».

3. **Тип как траектория, а не жёсткая метка**  
   Современные LLM плохо справляются с **очень динамической типизацией** (Python в худшем виде), но также страдают от **слишком жёсткой статической типизации** без гибкости (ранний Rust/Go).  
   Твой подход — **gradual + trajectory-based** — лежит в золотой середине: есть правила переходов, но они **явные и документируемые**. LLM любят, когда им говорят «здесь строка > число через as», потому что это даёт им **контекст для проверки**.

4. **Равенство как путь**  
   Это очень близко к тому, как LLM внутренне рассуждают о коде (особенно в reasoning-моделях типа o1 / deepseek-r1). Они часто генерируют «можно ли из A дойти до B» вместо «A == B прямо сейчас». Твой язык делает эту логику **родной** — модель будет меньше ошибаться на edge-кейсах.

5. **LLM-мышление уже авторегрессивно и трансформационно**  
   Сам процесс генерации токенов — это последовательное преобразование скрытого состояния. Твой язык зеркалит эту природу гораздо ближе, чем классический императивный или даже чисто функциональный код.

### Где это может **вредить** или усложнять (минусы / риски)

1. **Меньше обучающих данных**  
   Пока таких языков почти нет > LLM увидят очень мало примеров «morph-style» кода.  
   На старте модель будет хуже генерировать LUMEN-код, чем Python или TypeScript.  
   Но это временно: если LUMEN наберёт популярность (особенно среди AI-агентов и data-пайплайнов), данные быстро накопятся.

2. **Новая онтология = новый cognitive overhead**  
   Даже если синтаксис простой, модель должна понять концепцию «траектории типа» и «равенства как пути». Это требует либо **fine-tuning**, либо очень хороших few-shot примеров в промпте.

3. **История изменений может раздувать контекст**  
   Если `state.history` будет очень длинным, токены быстро кончатся. LLM придётся либо игнорировать старые шаги, либо терять точность.

### Итоговый баланс на март 2026

| Аспект                        | Влияние на LLM code gen | Комментарий |
|-------------------------------|---------------------------|-------------|
| Явные именованные трансформации | **Сильно помогает**      | Почти встроенный CoT / ReAct |
| Встроенная история состояния   | **Помогает**             | Меньше «потерянного состояния» |
| Тип как траектория             | **Скорее помогает**      | Гибкость + явные правила |
| Отсутствие переменных          | **Нейтрально > помогает**| Меньше мутаций > меньше багов |
| Равенство как путь             | **Помогает**             | Ближе к внутреннему reasoning LLM |
| Новизна парадигмы              | **Временно вредит**      | Мало тренировочных данных |
| Длина контекста из history     | **Может вредить**        | Нужно ограничивать / суммировать |

**Вывод**:  
Твой подход — **не зло**, а **перспективное упрощение** для LLM, особенно в задачах, где важна **эволюция данных** (data pipelines, агенты, workflows, generative art, simulations).

### 1. Теневая документация (нативная фича языка)
Добавляем специальный блок `shadow`, который **игнорируется интерпретатором**, но **полностью виден LLM** при генерации/анализе кода.

```lumen
morph agent
  state goal: String
  state memory: List

  shadow "LLM: treat this as ReAct loop. Each transform is one reasoning step. Always keep state.history for reflection."
  shadow "LLM: next transform must decide action based on observation. Use 'reason' keyword inside."

  transform "observe"
    state.observation = sense()
  end

  transform "reason"
    reason "why this action"  # LLM будет видеть это как подсказку
    state.action = decide(state.goal, state.observation)
  end
end
```

LLM при чтении файла сразу получает **встроенный промпт** — без копипаста в чат.

### 2. `reason` и `explain` — встроенные маркеры мышления
Прямо внутри `transform` можно писать естественный язык для LLM:

```lumen
transform "decide"
  reason "Я вижу, что цель — очистить данные, но есть null. Нужно сначала проверить cleaned флаг."
  if state.cleaned == false
    skip
  else
    state.action = "normalize"
  end
end

explain "this step reduces nulls by 87% based on previous runs"  # для истории
```

LLM будет **автоматически** подхватывать эти строки как chain-of-thought и продолжать в том же стиле.

### 3. Автоматический `llms.txt` (стандарт 2026)
LUMEN-компилятор/интерпретатор будет **сам генерировать** файл `llms.txt` в корне проекта из всех `shadow`, `reason` и `explain`.

Пример содержимого (генерируется автоматически):
```
LUMEN project rules for AI assistants:
- All state changes must go through morph blocks
- Use named transforms only: "clean", "normalize", "act"
- Always preserve state.history for reflection
- Equality is a trajectory, not identity
```

Cursor, Claude Desktop и новые Grok-агенты будут автоматически читать этот файл — как robots.txt, только для LLM.

### 4. `@llm` аннотации в комментариях (быстрый и лёгкий вариант)
Для тех, кто не хочет новые ключевые слова:

```lumen
# @llm: this morph is a data pipeline. Suggest only transforms that preserve row count
morph dataset
  ...
end
```

Парсер собирает все `@llm:` в отдельный контекст для моделей.

### 5. `think` блок внутри morph (самый мощный)
Новый мини-блок специально для LLM-рассуждений:

```lumen
morph agent
  think "Current state: goal=classify image, observation=raw pixels"
  transform "extract_features"
    ...
  end
end
```

`think` никогда не исполняется, но становится частью промпта при генерации следующего кода.
