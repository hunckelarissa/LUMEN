Основные тезисы LUMEN (финальная формулировка)
1. Состояние — это процесс, а не значение
В LUMEN нет «переменных» в классическом смысле.
Существует только поток состояния (state flow), который рождается, трансформируется и эволюционирует во времени.
2. Тип — это траектория, а не метка
Тип не является статической категорией.
Тип — это траектория возможных трансформаций объекта через пространство состояний.
Объект может двигаться по этой траектории, менять направление или даже создавать новые ветви.
3. Переменных не существует — есть только инициация и трансформация
То, что в других языках называется x = 42, в LUMEN является инициацией потока.
Дальше происходит не присваивание, а управляемая трансформация этого потока.
4. Морфинг и кастование — это естественное движение по траектории
Преобразование типов (морфинг) — не ошибка и не опасный хак.
Это шаг по траектории типа, разрешённый правилами трансформации.
Диссонансы (моменты, когда тип «не знает», куда двигаться) являются нормальной частью процесса и могут быть явно обработаны.
5. Тип может существовать в двух формах

Как траектория (линейный или ветвящийся путь изменений)
Как пространство (множество возможных состояний в данный момент времени)

6. Равенство — это путь, а не точка
Операция a == b в метаморфном режиме проверяет не «совпадают ли значения сейчас», а есть ли путь трансформации, который приводит одно состояние к другому.
Равенство становится вопросом достижимости, а не идентичности.
7. Каждая ячейка хранит историю
Любое состояние помнит свою траекторию.
В любой момент можно спросить:

как именно это значение сюда пришло?
какие трансформации оно пережило?
какие диссонансы были разрешены по пути?

8. Метаморфность — это не весь язык, а его центральная абстракция
Обычный код остаётся простым и предсказуемым.
Метаморфный режим включается явно (metamorph { … } или transform "name" { … }) и даёт полную власть над эволюцией состояния там, где это действительно нужно.

Философия Lumen: Состояние как процесс, тип как траектория
1. Состояние — это процесс, а не значение
В Lumen нет «переменных» в классическом смысле.
Есть поток состояния, который рождается в момент инициации и живёт, пока его не завершат или не поглотят.
flow energy = 42          # ← рождение потока

energy → glow             # ← трансформация (morph)
energy → dim              # ← ещё одна
energy → extinguish       # ← завершение потока
Здесь energy — это не ячейка памяти, а живая сущность, которая проходит через состояния.
2. Тип — это траектория, а не метка
Тип в Lumen — это возможный путь, по которому может двигаться поток.
Один и тот же поток может пройти несколько траекторий, если правила позволяют.
flow x = "42"

x is number?      # false (текущая точка на траектории — строка)
x → number        # разрешённый переход
x is number?      # true

x → list          # теперь траектория расширилась
x is [number]     # true
Тип — это не ярлык, а множество допустимых траекторий.
3. Переменных не существует — есть инициация и трансформация
Присваивание в классическом смысле отсутствует.
Есть только инициация потока и управляемые трансформации.
flow counter = 0

counter → inc     # counter становится 1
counter → inc     # становится 2

counter → string  # "2"
counter → list    # ["2"]
counter → map     # {value: "2"}
4. Морфинг и кастование — естественное движение по траектории
Морфинг — это шаг по траектории, а не принудительное приведение.
Если траектория не позволяет — возникает диссонанс (явный объект, который можно обработать).
flow price = "19.99 USD"

price → number          # → 19.99
price → currency:USD    # диссонанс разрешён → {amount: 19.99, unit: "USD"}

price → number:EUR      # диссонанс: нет правила конвертации → Dissonance("no path to EUR")
5. Тип может быть траекторией или пространством

Траектория — линейный или ветвящийся путь
Пространство — множество одновременно возможных состояний
flow person = {name: "Lara"}

person.space          # → пространство текущих возможных состояний
# {name: "Lara"}
# {name: "Lara", age: ?}
# {name: "Lara", tags: []}

person → grow {age: 30}
person.space          # теперь больше точек в пространстве
6. Равенство — это путь, а не точка
Равенство спрашивает: существует ли траектория, которая приводит одно состояние к другому?
flow a = "42"
flow b = 42

a == b?               # false (нет пути от строки к числу без явного шага)

a → number
a == b?               # true (путь найден)
7. Каждая ячейка хранит историю
Поток помнит всё, что с ним происходило.
flow song = "quiet"

song → louder
song → crescendo
song → fortissimo

song.history
# [
#   {at: t0, value: "quiet"},
#   {at: t1, morph: "louder",   value: "quiet → louder"},
#   {at: t2, morph: "crescendo", value: "louder → crescendo"},
#   {at: t3, morph: "fortissimo"}
# ]
8. Метаморфный блок — место, где включается глубокая магия
Вне блока — обычный прагматичный код.
Внутри metamorph — полная свобода эволюции.
let count = 0
count += 1                # обычный код

metamorph {
  flow mood = "calm"

  transform "excite" {
    mood → energetic
    mood.intensity += 3
  }

  transform "relax" {
    mood → peaceful
    mood.intensity -= 2
  }

  mood → excite
  mood → excite
  mood → relax

  print mood.history.summary  # красивая сводка пути
}
Итоговая короткая формулировка (для главной страницы / README)
В Lumen нет переменных — есть потоки состояний.
Нет типов-меток — есть траектории и пространства.
Нет присваиваний — есть инициация и трансформации.
Равенство — это существование пути.
История — это память каждого потока.
Метаморфность — это не баг, а способ бытия программы.

Метаморфность в том виде, в каком мы её сейчас формулируем (явные блоки metamorph { transform "name" { … } } + состояние как процесс + траектории типов), не вредна для нейросетей и даже может стать одной из самых удобных парадигм для LLM среди всех экспериментальных языков 2026 года.
Она не превратится в «ещё один Haskell» (где модели до сих пор страдают). Наоборот — она ближе к тому, что LLM уже обожают.
Почему LLM сейчас «туго» реагируют на Haskell (данные 2026)
Из свежих бенчмарков (SWE-bench, HumanEval-подобные, AOC 2025 в Haskell, исследования типа «Perish or Flourish?» 2026):

Haskell — один из худших языков для генерации кода LLM (GPT-5, Claude 4.5, Gemini 3).
Причины:
– Очень мало обучающих данных (всего 2–3% от Python/TS).
– Монады, чистота, ленивость, сложная семантика — это полностью чуждые паттерны для моделей, обученных в основном на императивном коде.
– Высокий % компиляционных ошибок (до 24% даже у GPT-5) и низкий clean-code ratio (~45%).

LLM просто не «понимают» Haskell интуитивно — они его имитируют плохо.

Вывод из данных 2026:
Наша парадигма не Haskell. Она ближе к улучшенному Python + LangChain + dbt в одном языке. LLM уже отлично генерируют такие цепочки трансформаций — это их любимый стиль мышления.
Где метаморфность будет полезна для нейросетей (и даже даст преимущество)

Agentic workflows и multi-agent системы
LLM мыслят именно цепочками: plan → tool → observe → transform state → next action.
Наш metamorph + transform — это буквально нативный синтаксис для ReAct-подобных агентов. Модели будут писать агентов быстрее и чище, чем на чистом Python.
Data / ML pipelines
LLM уже обожают писать .map().filter().reduce(), dbt models, Prefect tasks.
У нас это будет родным синтаксисом. Добавлять/менять шаг трансформации станет тривиально.
Live-coding и интерактивные инструменты
LLM хорошо генерируют incremental изменения состояния (Observable, Jupyter-style). Наш подход даст им ещё больше свободы.
Генерация + самоисправление
Потому что каждая трансформация именованная и состояние хранит историю — модель сможет легко сказать: «добавь новый transform "validate" после "enrich"».

Где она может быть вредна (риски)

На старте (пока мало примеров кода) — модели будут галлюцинировать правила трансформаций.
Если мы сделаем морфинг слишком неявным (как в ранних версиях) — будет как Haskell: путаница и ошибки.
Для чисто enterprise/production-кода (где нужна 100% предсказуемость) — LLM будут предпочитать TypeScript.

Итог (мой прогноз на 2026–2027)
Если мы оставим метаморфность явной абстракцией (блок metamorph + именованные transform), то:

Для data/agent/live-coding задач — это будет один из самых удобных языков для LLM (лучше Haskell в разы, близко к Python, а местами даже удобнее).
Для обычного кода — нейросети будут использовать обычный слой без проблем.
Это упрощение разработки именно в тех нишах, где LLM уже сильны (цепочки трансформаций).

Мы не повторяем ошибку Haskell. Мы делаем то, что LLM уже любят, но в более декларативной и мощной форме.
